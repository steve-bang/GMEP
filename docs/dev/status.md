# Trạng thái chi tiết các slice (chuyển từ CLAUDE.md)

Lịch sử và phạm vi từng slice đã build. `CLAUDE.md` chỉ giữ bản tóm tắt; đọc file này khi cần biết một slice đã làm gì, chưa làm gì, hoặc các quyết định BA đã áp dụng. Khi hoàn thành slice mới, cập nhật ở đây, không thêm vào `CLAUDE.md`.

Slices 0.3, 0.4, 1.1 (foundation), 1.2 (master data), 1.3 (CRM core), 1.4 (INV stock ledger), 1.5 (REC intake, quote and approval), 1.6 (REC repair order, execution, QC, handover) 1.7 (ACC money, SYS approvals), 1.8 (EIN basic invoice) and 1.9 core (RPT single-branch reports) are built and run end to end on the Firebase Emulator Suite (no GCP project yet). SYS has: password login + server session, lockout and rate limits, forgot/reset/invite/activate (dev email outbox), the 10-role BA permission matrix (data), working-branch scope picker, PII masking + "Hiện" + access log, document numbering service, effective-dated config with approval, notifications, audit viewer/export, branches/warehouses/users/roles/service catalog/price-list headers. CRM (slice 1.3, FR-CRM-001/002/004/010/011/013/014/017) has: customers (individual/business, MST) with contact data in a separate `customerPii` document, vehicles (company-unique plate registry, VIN, commercial flag, km), effective-dated ownership (owner change closes the open record, never edits history), cross-branch vehicle history as a white-listed projection read model (`VehicleHistoryRepository`, filled by REC later; empty-safe), exact cross-branch lookup by plate or full phone (projection P1/P2, phone searches access-logged) and `relateToWorkingBranch` (REC calls it on appointment/quote), consents with withdrawal and the marketing-audience filter, data-subject requests (state machine, assignee, deadline, delete = anonymisation behind `CustomerRetentionPort`, stub until REC/ACC), accent-insensitive search (name, phone, plate), customer export (`customer:export`, row cap, reason + password for full personal columns, audit + access log). Company-level records reach a branch scope through relation links (`customerLinks`, `vehicleLinks`; `branchIds` array on the record). **MFA is out of scope by owner decision ("làm sau")**: `StrongAuthPort` is a no-op hook. INV (slice 1.4, FR-INV-001/002/003/005/006/007/008/019/020/021/027, 009 as config) has: part catalogue (company-unique code and barcode slots, vehicle-line search), per-warehouse balances with the four numbers (available derived, RULE-008), GRN/GIN/RTN/ADJ documents (draft -> posted | cancelled, official number at posting, abnormal documents need a different approver, posted ones are reversed never edited, RULE-010), an append-only ledger (RULE-009) written in the same transaction as the balance, reservations (target quantity, idempotent, compared with available), weighted-average cost behind a `CostMethod` strategy chosen by the effective-dated `cost-method` config (integer VND, BigInt), reorder alert on available, standard list prices read from `price-item` config, the warehouse-deactivation guard, and a public `index.ts` API for REC (holdStock/releaseStock/issueForOrder/getAvailability). Transfers, stocktake, purchasing and lots are phase 2. REC (slice 1.5 first part, FR-REC-001/002/003/004/005/007; RULE-005/006/007) has: intake (5-step wizard, draft saved per step, vehicle/owner from CRM, odometer-below-last warning with reason per CRM C5, `relateToWorkingBranch` on opening a visit, numbering TX-), quote as its own object with a pure state machine (draft, sent, approved_full, approved_partial, rejected, expired; all transitions are wired), versions (an edit after sending is the next version, approved content is locked), labor lines (standard hours x hourly rate from effective-dated config, branch override) and part lines (list price from the `price-item` config with the version id kept on the line, available quantity only via INV `getAvailability`), discount only within the per-role `discount-limit` config, tax per line kind through the `tax-mapping` config (default key `vat`; key and version stored on every line; missing rate blocks the quote; a warning when the validity crosses a tax change), totals per BA C6 (subtotal before tax and before order discount), no stock hold before approval, REC permissions in the role matrix, demo services/hours/rate/tax/limits as sample config. BA §17 is applied (`docs/dev/ba-answers-for-dev.md`): service types are the `service-type` catalogue, labor lines carry a "differs from standard hours" flag, ONE odometer threshold (`abnormalKmDrop`, CRM) and the vehicle's km is updated when an intake completes (`recordOdometer`), quote expiry is derived at read time and the state machine refuses to approve an expired quote, `sentVia` (never claims a message was sent), notifications through SYS `notifyUsers` (INV shortened holds, abnormal km, lookup limit), REC joins the retention gate (still unverified until orders/payments/invoices connect), goods issues for orders carry the immutable `lineKey`, the `transfer-order` source is hidden outside local/test, consent evidence is an `evidence-kind` catalogue, QV lost `customer-lookup-customer:view`, history outside the scope needs `vehicle-history-cross:view`, relation sources `intake` and `quote`. REC approval (slice 1.5 second part, FR-REC-008/009/023/026/030/031/032): approval full/partial by item (customer link, counter signature, counter verbal = exception), evidence with SHA-256 hash, content locked, expired quotes refused, a refused required item needs a catalogue reason (config `quote-approval`, `decline-reason`), tokenised login-free link (only the hash stored, token in the body of the decision routes, rate limited, uniform 404), customer page `/b/[token]`, A4 print, SYS notifications; hand-over for 1.6 is `getApprovedQuote` (lineKey, price version, tax key), `allocateRepairOrderNumber`, `getServiceWorkflow`. Not built in REC yet: repair order and repair items (1.6), supplementary quotes, photos, Zalo/SMS/email channels and OTP (locked), signature image (needs file storage). **Slice 1.6** (REC, FR-REC-010/012-017/021/022/028): the approval opens the repair order (idempotent, only approved lines, stock hold), separate machines for order and item, technician tablet with time events, part requests that issue stock in the same transaction, QC with an effective-dated checklist, handover, cancel with returns. **Slice 1.7** (ACC money, SYS approvals; FR-ACC-001/002/003/004, 006 minimal, 009 reused from the tax config, FR-SYS-004; RULE-007/010/011; R44): receipts with several methods (cash, transfer, card, QR recorded by hand; no gateway), deposits applied to the order, the cash book per branch (append-only entries, running balance), one open shift per branch with a counted-vs-book variance (cause, explanation, manager approval above the tolerance), day close (blocked by an open shift or an unapproved difference; a closed day takes no more documents), reversal entries (a posted payment is never updated: request, a different manager approves, the requester executes once), expense vouchers over the effective-dated `approval-limit` need approval first, the approved debt at handover, and `getOrderBalance` (receivable from the order incl. approved supplements; received = receipts + applied deposits - reversed). SYS has the minimal approval workflow (requester never decides, level 1 manager / level 2 owner, handler or execute-once). REC applies BA section 19: the handover reads ACC inside its own transaction (`handoverRequiresPayment` default true, figures kept on the record, manager exception with reason when ACC is down), a supplementary quote cannot be approved on a closed order and closes with it, reopen voids the old QC result, handover only CV/QL, CV cancels only untouched approved orders, fifth pause code, `quote-verbal-over-limit:approve`, warehouse-missing notice, an order with money cannot be cancelled. Firestore transactions must finish all reads before the first write (README). The composite-index budget is nearly used: 191 of 200 after slice 1.8. **Slice 1.8** (EIN basic invoice; FR-EIN-001..006, 009, 010, 011, 013, minimal 007; RULE-005/007/010; R68): provider-agnostic `EInvoiceProvider` port (idempotent by a stable client key, typed errors, neutral statuses) with the scriptable `FakeProvider` as the ONLY adapter (test environment; an issuer on `live` with `fake` is "not activated"); the invoice and the issue request are separate pure state machines and the order never carries an invoice status; issuing is from a repair order only, with a checklist that lists every blocking issue (buyer retail/business, tax key/version/rate taken from the approved lines, invoice total must equal the order total); no duplicate by a deterministic request id created in the same transaction as the order index, the provider is never called inside a transaction and is ASKED by the key before any resend; the error queue is one bounded document per branch with retry, fix-buyer and cancel (one last query), plus a due-job endpoint instead of a scheduler; XML and PDF go to Cloud Storage through a minimal `FileStore` port and are served after a Scope check; adjust, replace and cancel use the SYS approval workflow (`invoice:approve` = the "chief accountant" right, by default the owner only; step-up password for a cancel); buyer address and e-mail live in `invoicePii` and follow the PII policy; config `einvoice-issuer` and `einvoice-policy`. ONE new composite index (`invoices.byBranch`): 191 of 200, and `pnpm check:indexes` warns from 190 and fails above 195 (R68), so slice 1.9 keeps at least four. BA section 20 items paid in the same stretch: `expense-category.sourceRequirement` and a mandatory reason for a voucher without a source document, which then always needs a manager (R64); a running per-shift cap on the cashier's own approval tier (R58); `deposit_refund` as its own approval kind, never self-decided (R57). Not built in EIN: a real provider, sending the invoice to the customer (FR-EIN-008), the timing/deposit rule (FR-EIN-012), the thirteen wrong-invoice cases of Thông tư 91/2026, a scheduler for the retry job. **BA section 21 applied (R72, R75, R77)**: `taxChangePolicy` defaults to `block` for any issuer that is live or not `fake` (`defaultTaxChangePolicy`; `warn` only for the fake in the test environment; an explicit config value still wins); EIN `hasValidInvoice(orderId)` is wired through a port per module (`OrderInvoiceGate` in REC, INV and ACC, bridged only in `composition/einWiring.ts`) into REC cancel order, INV return (RTN for an order, reversal of an order's issue) and ACC payment reversal and deposit refund, error `order_has_valid_invoice` (409), fail closed as `invoice_check_unavailable`; every XML/PDF download is written to the PII access log. Slices 1.5 to 1.9 are built; the e2e of slice 1.9 passes. Known gap on R70: BA text says the owner may self-approve with a `selfApproved` flag, the BA table says nobody self-approves; the code follows the stricter reading (the owner holds `invoice:approve` but not `invoice-correction:create`, SYS refuses self-decision), so no flag exists; BA to settle. Not built in ACC: refund to the customer, advance credit, reopening a closed day, period lock, payables, accounting export, bank reconciliation, aging by customer, reminders. **Slice 1.9 core** (RPT single branch; FR-RPT-001, 003, 004 minimum, 011, 012, 013, 014; RULE-007, R68): `src/modules/rpt` keeps ONE read-model document per branch and business day (`rollups/<branchId>_<yyyyMMdd>`, read by key, NO new index: still 191/200). `computeDaily` is a pure function over facts (orders and their approved lines, payments, open debts, cash shifts, issued invoices, goods issues) that `composition/rptWiring.ts` reads from the public REC/ACC/EIN/INV repositories inside one branch Scope; a content hash makes the job idempotent (an unchanged day writes nothing, a changed day writes the document and its audit entry in one transaction; a rebuild from nothing equals the incremental refresh). Jobs: `POST /api/v1/rpt/jobs/run-due` (today, yesterday, missing days of the last 7; a closed = official day is skipped) and `.../rebuild {date}`; there is no scheduler. Reads: dashboard (role lens; every block and alert is cut on the SERVER by the view permission of its source module, revenue by `report-daily:view`; several branches = the owner's table summed from each branch document), daily report (formula printed, received + open debt = order total reconciliation, 7-day trend), drill-down to source documents, exception alerts (open too long, unpaid after handover, overdue debt, no invoice, cash variance, goods issue without source = 0), CSV export (`report-daily:export`, one branch, audited). Thresholds are the effective-dated `report-policy` config; caps are `RptConfig` and the screens say "mức tối thiểu" when a scan was cut. Permissions top-up `2026-11-rpt-1.9-reports`. Not built in RPT: monthly report and comparison, four-way reconciliation (FR-RPT-004 full), branch comparison (RPT-002), receivable aging (RPT-007), warehouse / worker / customer reports, gross profit, filters by service type / employee, advanced charts, scheduler, PDF/Excel, an incremental in-transaction projection (R87).
